# Final Data Exploration Conclusions

## Status

The data exploration phase is complete. The dataset now has a verified path from a user concept to a Census measure and from a Census Block Group (CBG) to a human-readable state and county.

~~~
User question
    ↓
Field metadata
    ↓
Census variable and CBG data column
    ↓
CBG identifier
    ↓
State / county FIPS extraction
    ↓
State and county names
~~~

## What was established

### 1. Dataset structure

The database contains parallel 2019 and 2020 CBG-level Census releases. Main tables are organized by Census subject families, for example 2019_CBG_B01, and have one record per Census Block Group. A full Census variable is stored as a column in a subject table; for example, **B01001e10** is a column in **2019_CBG_B01**.

The dataset includes:

- CBG data tables with Census measures;
- field-description metadata that defines each measure;
- geographic data with coordinates and land/water area;
- FIPS reference data with state and county labels.

### 2. Variable meaning is available in metadata

The field-description metadata supplies a usable semantic layer. It contains the variable identifier, subject table, title, topic, universe, and hierarchical field levels.

For example, the metadata resolves **B01001e10** to:

~~~
Estimate
> Sex by Age
> Total population
> Total
> Male
> 22 to 24 years
~~~

Therefore, a compact Census column name can be represented as a readable semantic path. Estimate and margin-of-error fields are separate: estimates are the normal default, while margins of error must be returned only when uncertainty is requested.

### 3. Metadata retrieval is feasible, but requires controlled ranking

The retrieval experiments proved that a complete semantic path can find the intended variable for the tested question:

~~~
“males aged 22 to 24” → B01001e10
~~~

They also showed why raw keyword matching is not enough:

- a search restricted to the wrong metadata levels returns no result;
- broad terms such as *income* and *poverty* return many relevant-but-not-identical candidates;
- substring matching makes *male* match *female*;
- both estimate and margin-of-error fields can be returned unless deliberately filtered.

The implication is clear: metadata retrieval should start with lexical search over a combined semantic path, then apply token-aware matching, concept ranking, population/universe checks, and a default preference for estimate fields. Embeddings are not required for the first implementation; they remain an option if the lexical baseline performs poorly on a larger test set.

### 4. CBG-to-state/county geography join is verified

The join was tested with data from **2019_CBG_B19** and the **2019_METADATA_CBG_FIPS_CODES** reference table:

~~~sql
SELECT
    b.CENSUS_BLOCK_GROUP,
    LEFT(b.CENSUS_BLOCK_GROUP, 2) AS STATE_FIPS_FROM_CBG,
    SUBSTR(b.CENSUS_BLOCK_GROUP, 3, 3) AS COUNTY_FIPS_FROM_CBG,
    f.STATE,
    f.STATE_FIPS,
    f.COUNTY_FIPS,
    f.COUNTY
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_CBG_B19" b
LEFT JOIN US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIPS_CODES" f
    ON LEFT(b.CENSUS_BLOCK_GROUP, 2) = f.STATE_FIPS
   AND SUBSTR(b.CENSUS_BLOCK_GROUP, 3, 3) = f.COUNTY_FIPS
LIMIT 20;
~~~

All 20 sampled records matched without null values. For example:

| CBG | Extracted state FIPS | Extracted county FIPS | Resolved geography |
| --- | --- | --- | --- |
| 181691022001 | 18 | 169 | IN, Wabash County |

The deterministic geography rule is:

~~~text
CENSUS_BLOCK_GROUP
  first 2 digits  → STATE_FIPS
  next 3 digits   → COUNTY_FIPS

(STATE_FIPS, COUNTY_FIPS) → FIPS_CODES → STATE, COUNTY
~~~

This rule can now be used by the query planner for state- and county-level filters, grouping, and display labels.

## Final conclusion

The core data dependencies for the agent are understood:

| Capability | Status | Implementation implication |

Exploration should stop here. The remaining work is product and engineering work: construct the catalog, build the deterministic query pipeline, and evaluate it with a question set.

## Next implementation plan

### Phase 1 — Build the VariableCatalog

Create a refreshable Python job that reads field metadata and verified physical table schemas. It must create one catalog record per variable:

~~~python
Variable(
    year=2019,
    table_id="B01001e10",
    table_number="B01001",
    physical_table="2019_CBG_B01",
    physical_column="B01001e10",
    measure_type="estimate",
    title="Sex By Age",
    universe="Total population",
    semantic_path=[
        "estimate", "sex by age", "total population",
        "total", "male", "22 to 24 years",
    ],
)
~~~

The physical table and column are allow-listed from observed schemas. They must never be constructed directly from user input.

### Phase 2 — Implement lexical variable retrieval

Convert every catalog record into normalized text and tokens. Parse a question into concepts, then retrieve and score candidates across title, universe, topic, and semantic path.

The first scorer should:

1. normalize synonyms and number forms, such as 22–24 to 22 to 24;
2. require whole-token and exact-phrase matches where appropriate;
3. reward matches for requested statistic, population, and age/sex qualifiers;
4. prefer estimates and penalize margins of error unless requested;
5. return a clarification instead of choosing when candidates are ambiguous.

Build a small evaluation set of representative population, income, housing, and poverty questions. Measure whether the correct variable is in the top candidates before adding embeddings or an LLM retrieval layer.

### Phase 3 — Parse the user question into a QueryPlan

Extract a controlled intent: selected variable, year, aggregation, geography filter, grouping, sort order, and requested uncertainty. The parser may use rules or an LLM constrained to a JSON schema, but its output must be validated against the catalog.

~~~python
QueryPlan(
    year=2019,
    source_table="2019_CBG_B01",
    value_column="B01001e10",
    aggregation="SUM",
    geography_filter={"state": "IN"},
    group_by=["county"],
    include_margin_of_error=False,
)
~~~

### Phase 4 — Compile and validate SQL

Generate SQL only from templates and the validated QueryPlan:

- table and column names come from the VariableCatalog;
- state/county joins use the verified CBG FIPS extraction rule;
- values use bound query parameters;
- only read-only SELECT queries are allowed;
- detail queries have a fixed limit;
- cross-year combinations require an explicit supported comparison plan.

### Phase 5 — Execute and explain the answer

Run the validated SQL in Snowflake and return both the numerical result and its provenance:

~~~text
result
+ selected Census variable and semantic definition
+ year and geographic scope
+ aggregation used
+ optional margin of error
+ generated SQL for inspection
~~~

This produces grounded answers: every value can be traced from the user question through metadata, a selected Census variable, a validated query plan, and the Snowflake result.
