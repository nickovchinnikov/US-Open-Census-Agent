# Experiment 2 — From a User Question to a Census Variable and SQL

## Goal

This experiment evaluates **metadata retrieval only**. Before building an agent or generating analytical SQL, it asks a narrower question:

> Can a natural-language question be mapped to the correct Census variable by searching the 2019 metadata table with ordinary SQL?

Each metadata record contains a variable identifier (**TABLE_ID**), Census table (**TABLE_NUMBER**), title, topic, and a hierarchical definition in **FIELD_LEVEL_1** through **FIELD_LEVEL_10**.

~~~
User wording → metadata fields / semantic path → TABLE_ID → physical CBG column
~~~

The CSV files below preserve the actual outputs:

- [Income search output](median_household_income.csv)
- [Poverty search output](people_are_living_below_the_poverty_level.csv)
- [B01001 hierarchy inspection](metadata_B01001e10.csv)
- [Combined semantic-path output](median_household_income2.csv)

## Experiment 1 — Exact demographic concept

**Question:** “How many males aged 22 to 24 are there?”

**Tested query:**

~~~sql
SELECT
    TABLE_ID,
    TABLE_NUMBER,
    TABLE_TITLE,
    TABLE_TOPICS,
    FIELD_LEVEL_1,
    FIELD_LEVEL_2,
    FIELD_LEVEL_3,
    FIELD_LEVEL_4
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIELD_DESCRIPTIONS"
WHERE
    LOWER(FIELD_LEVEL_1) LIKE '%male%'
    AND LOWER(FIELD_LEVEL_2) LIKE '%22 to 24%'
ORDER BY TABLE_ID;
~~~

**Observed result:** no rows.

**Why:** the target exists, but the query searched the wrong levels. The later inspection shows that **Male** is in **FIELD_LEVEL_5** and **22 to 24 years** is in **FIELD_LEVEL_6**, not levels 1 and 2.

~~~
TABLE_ID: B01001e10
TABLE:    B01001 — Sex By Age
PATH:     Estimate > SEX BY AGE > Total population > Total > Male > 22 to 24 years
~~~

**Result:** this does not mean lexical retrieval failed. It means a retriever cannot assume that a concept is always located at the same metadata level.

## Experiment 2 — Common language: median household income

**Question:** “What is the median household income?”

**Tested query:**

~~~sql
SELECT
    TABLE_ID,
    TABLE_NUMBER,
    TABLE_TITLE,
    TABLE_TOPICS,
    FIELD_LEVEL_1,
    FIELD_LEVEL_2,
    FIELD_LEVEL_3,
    FIELD_LEVEL_4
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIELD_DESCRIPTIONS"
WHERE
    LOWER(TABLE_TITLE) LIKE '%income%'
    OR LOWER(FIELD_LEVEL_1) LIKE '%income%'
    OR LOWER(FIELD_LEVEL_2) LIKE '%income%'
    OR LOWER(FIELD_LEVEL_3) LIKE '%income%'
ORDER BY TABLE_ID
LIMIT 30;
~~~

**Observed result:** the query reached its 30-row limit. The result contains 10 records from **B17011** (*Aggregate Income Deficit*) and 20 records from **B19001** (*Household Income* distribution).

**Interpretation:** the word *income* finds the general domain but is too broad to select the exact measure. The output is sorted by variable code, not relevance, and the intended *median* measure is not selected in the first 30 rows. The retriever must preserve *median* as a required concept and rank candidates.

## Experiment 3 — Poverty concept

**Question:** “How many people are living below the poverty level?”

**Tested query:**

~~~sql
SELECT
    TABLE_ID,
    TABLE_NUMBER,
    TABLE_TITLE,
    TABLE_TOPICS,
    FIELD_LEVEL_1,
    FIELD_LEVEL_2,
    FIELD_LEVEL_3,
    FIELD_LEVEL_4
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIELD_DESCRIPTIONS"
WHERE
    LOWER(TABLE_TITLE) LIKE '%poverty%'
    OR LOWER(FIELD_LEVEL_1) LIKE '%poverty%'
    OR LOWER(FIELD_LEVEL_2) LIKE '%poverty%'
    OR LOWER(FIELD_LEVEL_3) LIKE '%poverty%'
    OR LOWER(FIELD_LEVEL_4) LIKE '%poverty%'
ORDER BY TABLE_ID
LIMIT 50;
~~~

**Observed result:** the query reached its 50-row limit; all 50 rows are from **B17010**, a table about poverty status of **families** by family type and related children.

**Interpretation:** the search identifies the poverty domain but does not prove that it selected the measure meant by “people.” Sorting by **TABLE_ID** also concentrates many rows from a single table. The engine must distinguish target populations—people, families, children, households—and rank individual fields before selection.

## Experiment 4 — Inspect the true metadata hierarchy

**Tested query:**

~~~sql
SELECT
    TABLE_ID,
    TABLE_NUMBER,
    TABLE_TITLE,
    FIELD_LEVEL_1,
    FIELD_LEVEL_2,
    FIELD_LEVEL_3,
    FIELD_LEVEL_4,
    FIELD_LEVEL_5,
    FIELD_LEVEL_6,
    FIELD_LEVEL_7,
    FIELD_LEVEL_8,
    FIELD_LEVEL_9,
    FIELD_LEVEL_10
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIELD_DESCRIPTIONS"
WHERE TABLE_NUMBER = 'B01001'
ORDER BY TABLE_ID;
~~~

**Observed result:** the target variable is explicitly encoded as:

~~~
B01001e10
Estimate > SEX BY AGE > Total population > Total > Male > 22 to 24 years
~~~

**Result:** a Census field is a hierarchy, not a fixed pair of labels. All field levels must be searched together.

## Experiment 5 — Search a combined semantic path

**Hypothesis:** concatenate all field levels and search the completed path rather than fixed column positions.

**Tested query:**

~~~sql
SELECT
    TABLE_ID,
    TABLE_NUMBER,
    TABLE_TITLE,
    ARRAY_TO_STRING(
        ARRAY_CONSTRUCT_COMPACT(
            FIELD_LEVEL_1, FIELD_LEVEL_2, FIELD_LEVEL_3, FIELD_LEVEL_4,
            FIELD_LEVEL_5, FIELD_LEVEL_6, FIELD_LEVEL_7, FIELD_LEVEL_8
        ),
        ' > '
    ) AS SEMANTIC_PATH
FROM US_OPEN_CENSUS_DATA_NEIGHBORHOOD_INSIGHTS_FREE_DATASET.PUBLIC."2019_METADATA_CBG_FIELD_DESCRIPTIONS"
WHERE TABLE_NUMBER = 'B01001'
  AND LOWER(
        ARRAY_TO_STRING(
            ARRAY_CONSTRUCT_COMPACT(
                FIELD_LEVEL_1, FIELD_LEVEL_2, FIELD_LEVEL_3, FIELD_LEVEL_4,
                FIELD_LEVEL_5, FIELD_LEVEL_6, FIELD_LEVEL_7, FIELD_LEVEL_8
            ),
            ' '
        )
      ) LIKE '%male%22 to 24%';
~~~

**Observed result:** four records were returned:

| Candidate | Why it matched | Desired? |
| --- | --- | --- |
| **B01001e10** | Estimate; Male; 22 to 24 years | Yes |
| **B01001e34** | The substring *male* occurs in *Female*; 22 to 24 years | No |
| **B01001m10** | Margin of error; Male; 22 to 24 years | Usually no |
| **B01001m34** | Margin of error; *male* inside *Female*; 22 to 24 years | No |

**Result:** the semantic-path representation retrieves the correct variable, so it is a good lexical baseline. A production retriever must use whole-token matching (*male*, not the substring inside *female*) and exclude **MarginOfError** fields unless uncertainty is requested.

## Overall conclusion

The metadata is sufficient to build a first retrieval layer without embeddings. Plain **ILIKE** plus **ORDER BY TABLE_ID** can only generate candidates; it cannot reliably choose the final Census variable. The next baseline should search a materialized semantic path, score every query concept, enforce estimate/population constraints, and ask a clarification question if leading candidates are still close.

## High-level design of the Python engine

### 1. Build a local variable catalog

At startup or in a scheduled refresh, Python reads the field-description metadata and creates one normalized catalog record per variable:

~~~
VariableCatalog
  year                2019
  table_id            B01001e10
  census_table        B01001
  physical_table      2019_CBG_B01
  physical_column     B01001e10
  measure_type        estimate | margin_of_error
  title / topics / universe
  semantic_path       Estimate > ... > Male > 22 to 24 years
  searchable_tokens   [sex, age, population, male, 22, 24]
~~~

The physical table must come from a verified table-to-column mapping, not from guessing based only on a variable code. The catalog also records the years and columns that actually exist, preventing the SQL builder from inventing a table or column.

### 2. Turn the question into structured intent

Rules, an LLM constrained to JSON, or both parse the input into a small schema:

~~~python
Intent(
    measure="count",
    concepts=["male", "22 to 24 years"],
    population="total population",
    geography=None,
    year=2019,
    aggregation="sum",
    include_margin_of_error=False,
)
~~~

The parser normalizes wording and numbers (for example, **22–24** to **22 to 24**) and keeps important qualifiers such as *median*, *family*, *household*, *male*, and *estimate*. These are constraints and ranking signals, not optional keywords.

### 3. Retrieve and resolve variables

The retriever searches semantic paths, titles, topics, and universes across the chosen year. It uses token and phrase matching, so *male* never matches *female*.

Candidates are ranked with explicit evidence:

~~~
exact phrase + all required concepts + matching population/universe
+ matching statistic (for example, median) + estimate preference
- missing qualifier - margin-of-error penalty - conflicting population
~~~

The resolver selects a variable only if it clearly outranks alternatives. Otherwise, it returns a focused clarification, such as “Do you mean people or families below the poverty level?”

### 4. Create a safe query plan

The resolver creates a **QueryPlan**, not unrestricted SQL:

~~~python
QueryPlan(
    source_table="2019_CBG_B01",
    value_column="B01001e10",
    select_expression='SUM("B01001e10")',
    filters=[],
    group_by=[],
    order_by=[],
    limit=100,
)
~~~

Geography, aggregation, ranking, and year are added only when present in the question and supported by verified catalog entries. State/county filters cannot be planned until the CBG-to-geography join is verified.

### 5. Compile, validate, and execute SQL

The compiler renders fixed SQL templates from **QueryPlan**. Table and column identifiers come only from the catalog allow-list; user values are bound as Snowflake parameters. The validator enforces:

- read-only SELECT statements;
- an allow-listed year, table, and variable column;
- no cross-year combination unless explicitly planned;
- a row limit for detail queries;
- joins only from the verified geography map.

The final answer returns the numeric result, selected variable, semantic path, year, aggregation, and generated SQL. This makes each answer inspectable and lets the user correct an ambiguous interpretation.

~~~python
def answer_question(question: str) -> Answer:
    intent = intent_parser.parse(question)
    candidates = catalog.search(intent, year=intent.year)
    variable = resolver.select_or_clarify(candidates, intent)
    plan = planner.create(intent, variable, catalog)
    sql, params = compiler.render(plan)
    validator.assert_safe(sql, plan, catalog)
    rows = snowflake.execute(sql, params)
    return presenter.make_answer(rows, variable, plan, sql)
~~~

Natural language therefore never writes unrestricted SQL directly: it selects a controlled intent and a catalog variable; the planner and compiler build the final query.
